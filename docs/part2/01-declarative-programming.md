# 2.1 声明式编程

在本书的第一部分，我一直在论证：范畴论和编程，说到底都是关于**可复合性**的。编程时，你不断地把问题拆小，
直到细节小到你能对付为止；然后逐个解决子问题，再自底向上地把解答重新复合起来。粗略地说，做这件事有两种方式：
告诉计算机**做什么**，或者告诉它**怎么做**。前者叫**声明式**（declarative），后者叫**命令式**（imperative）。

哪怕在最基础的层面上，你也能看到这一点。复合本身就可以用声明式的方式来定义——比如说，`h` 是 `g` 在 `f` 之后的复合：

```lean hidden
def f (n : Nat) : Nat := n + 1
def g (n : Nat) : String := toString n
```

```lean
def h : Nat → String := g ∘ f
```

也可以用命令式的方式来定义——先调用 `f`，记住这次调用的结果，然后用这个结果去调用 `g`：

```lean
def h' (x : Nat) : String :=
  let y := f x
  g y
```

（这里的 `f` 和 `g` 是随便取的两个函数：`f n = n + 1`，`g n = toString n`。）

命令式版本的程序，通常被描述为一串按**时间**排列的动作。尤其是，对 `g` 的调用不能在 `f` 执行完毕之前发生。
至少，概念上的图景是这样的——在惰性语言里，参数按**需要时才求值**（call-by-need）的方式传递，实际的执行顺序可能另有不同。

::: tip Lean 深入：Lean 是严格求值的
Haskell 是惰性语言：`let y := f x` 并不会立刻计算 `f x`，而是等到真正用到 `y` 时才算。
Lean 和 Rust 一样是**严格**（strict）求值的：`let y := f x` 会先把 `f x` 算出来。
需要惰性时，Lean 提供显式的 `Thunk`：`Thunk.mk (fun _ => f x)` 把计算包起来，`.get` 时才执行（并缓存结果）——
这和 Rust 的 `std::cell::LazyCell`、`OnceCell` 是一个思路。
:::

事实上，取决于编译器有多聪明，声明式代码和命令式代码在执行方式上可能几乎没有区别，甚至完全没有区别。
在 Lean 里，我们可以把这句话变成一条定理——两种写法定义的是**同一个**函数，而且 Lean 一眼就能看出来（`rfl`：按定义展开后两边逐字相同）：

```lean
theorem h_eq_h' : h = h' := rfl
```

但这两种方法论在我们**着手解决问题的方式**上、在最终代码的**可维护性**与**可测试性**上，有时差别巨大。

::: tip Rust 视角：循环 vs 迭代器管道
Rust 程序员每天都在这两种风格之间选择。下面两个函数都计算“偶数的平方和”：

```rust
/// 命令式：描述“怎么做”——维护一个可变的累加器，一步步更新它。
fn sum_even_squares_loop(xs: &[u64]) -> u64 {
    let mut total = 0;
    for &x in xs {
        if x % 2 == 0 {
            total += x * x;
        }
    }
    total
}

/// 声明式：描述“是什么”——偶数的、平方的、和。
fn sum_even_squares_iter(xs: &[u64]) -> u64 {
    xs.iter().filter(|&&x| x % 2 == 0).map(|&x| x * x).sum()
}
```

迭代器版本是由小零件（`filter`、`map`、`sum`）**复合**而成的；每个零件都可以单独理解、单独测试，换掉其中一个也不影响其他。
而在优化之后，rustc 往往会为两者生成几乎相同的机器码——这正是上面那句“取决于编译器有多聪明”。
:::

Lean 也有命令式的 `do` 记法：`let mut` 声明可变变量，`for` 写循环。下面是同一个计算的两种写法，
以及一条证明它们对**所有**输入都相等的定理：

```lean
/-- 命令式：可变累加器 + for 循环。 -/
def sumSqImp (xs : List Nat) : Nat := Id.run do
  let mut s := 0
  for x in xs do
    s := s + x * x
  return s

/-- 声明式：先把每个元素平方，再把它们加起来。 -/
def sumSqDecl (xs : List Nat) : Nat :=
  (xs.map (fun x => x * x)).foldl (· + ·) 0

#guard sumSqImp [1, 2, 3] == 14
#guard sumSqDecl [1, 2, 3] == 14

theorem sumSq_same (xs : List Nat) : sumSqImp xs = sumSqDecl xs := by
  simp [sumSqImp, sumSqDecl, List.foldl_map]
```

::: tip Lean 深入：`Id.run do`
Lean 的 `do` 块并不是“真的”可变状态：编译器会把 `let mut` 和 `for` 翻译成纯函数——本质上就是一次 `foldl`。
`Id` 是“什么副作用都没有”的单子，`Id.run` 把结果取出来。所以 `sumSqImp` 虽然**写起来**是命令式的，**骨子里**仍是一个纯函数，
这也是 `simp` 能把它化归为 `foldl` 并证明两者相等的原因。`#guard e` 会在编译时求值布尔表达式 `e`，为假就报错。
:::

核心问题是：面对一个问题，我们是否总能在声明式和命令式两种解法之间选择？而且，如果存在声明式的解法，它是否总能被翻译成计算机代码？
这个问题的答案远非显而易见；如果我们能找到它，大概会彻底改变我们对宇宙的理解。

![小行星游戏](/img/2.1/asteroids.png "小行星（Asteroids）游戏：飞船的运动，就是牛顿运动定律的逐帧数值积分。")

让我详细说说。物理学中也有一种类似的二元性，它要么指向某个深层的基本原理，要么告诉了我们一些关于人类思维如何运作的事情。
理查德·费曼（Richard Feynman）提到过，这种二元性启发了他在量子电动力学方面的工作。

大多数物理定律都有两种表达形式。一种利用**局部的**、或者说**无穷小的**考量：我们观察系统在某个小邻域里的状态，
预测它在下一瞬间会如何演化。这通常表达为**微分方程**，需要在一段时间上积分（也就是累加）起来。

::: info 数学小课堂：导数与微分方程
**导数** $\frac{dx}{dt}$ 描述“$x$ 随时间 $t$ 变化得有多快”：在极短的时间 $\Delta t$ 里，$x$ 大约改变了 $\frac{dx}{dt} \cdot \Delta t$。
比如位置对时间的导数就是速度，速度对时间的导数就是加速度。

**微分方程**是一条关于导数的方程，比如“速度等于位置的导数”。它不直接告诉你答案（某一时刻的位置），
而是告诉你**每一瞬间该怎么变**。要得到答案，你得从起点出发，把这些微小的变化一点点**累加**（积分）起来。
这正是计算机模拟要做的事：选一个很小的 $\Delta t$，然后反复执行“位置 += 速度 × Δt；速度 += 加速度 × Δt”。
:::

注意，这种方法多么像命令式思维：我们沿着一串小步骤走到最终的解，每一步都依赖于上一步的结果。
事实上，物理系统的计算机模拟，通常就是把微分方程变成**差分方程**再反复迭代来实现的。小行星游戏里的飞船就是这样动起来的。
在每个时间步，飞船的位置都加上一个小增量，这个增量由速度乘以时间步长得到。而速度本身又加上一个与加速度成正比的小增量，
加速度则由力除以质量给出。

用 Lean 写出来就是一个“单步”函数，再加上一个把它重复 $n$ 次的循环：

```lean
structure Ship where
  pos : Float
  vel : Float
deriving Repr

/-- 一个时间步：位置加上 速度×dt，速度加上 (力/质量)×dt。 -/
def step (force mass dt : Float) (s : Ship) : Ship :=
  let acc := force / mass
  { pos := s.pos + s.vel * dt, vel := s.vel + acc * dt }

/-- 把单步重复 n 次（`Nat.repeat f n x` 就是 f (f (… (f x)))）。 -/
def simulate (n : Nat) (s : Ship) : Ship :=
  Nat.repeat (step 2.0 1.0 0.01) n s

#eval simulate 100 ⟨0, 0⟩   -- { pos := 0.990000, vel := 2.000000 }
```

这些正是牛顿运动定律所对应的微分方程的直接编码：

$$F = m \frac{dv}{dt} \qquad v = \frac{dx}{dt}$$

类似的方法可以用于更复杂的问题，比如用麦克斯韦方程组计算电磁场的传播，甚至用格点 QCD（量子色动力学）研究质子内部夸克和胶子的行为。

这种局部思维，加上数字计算机所鼓励的空间与时间的离散化，在斯蒂芬·沃尔夫拉姆（Stephen Wolfram）的英雄式尝试中达到了极致：
他试图把整个宇宙的复杂性归结为一个元胞自动机系统。

另一种方法是**全局的**。我们观察系统的初始状态和最终状态，通过使某个**泛函**取最小值，算出连接两者的轨迹。
最简单的例子是**费马最短时间原理**。它说：光线沿着使其传播时间最短的路径传播。特别地，在没有反射或折射物体的情况下，
从点 $A$ 到点 $B$ 的光线会走最短的路径，也就是一条直线。但光在致密的（透明）材料中，比如水或玻璃里，传播得更慢。
所以，如果起点在空气中、终点在水下，光在空气中多走一段、然后抄近路穿过水，就更划算。
用时最短的路径会让光线在空气与水的分界面上**折射**，由此得到斯涅尔折射定律：

$$\frac{\sin(\theta_1)}{\sin(\theta_2)} = \frac{v_1}{v_2}$$

其中 $v_1$ 是空气中的光速，$v_2$ 是水中的光速。

![斯涅尔定律](/img/2.1/snell.jpg "光从空气进入水中时发生折射：入射角 θ₁ 与折射角 θ₂ 的正弦之比，等于两种介质中光速之比。")

::: info 数学小课堂：泛函与“取最小值”
普通的函数把一个**数**映到一个数；**泛函**（functional）把一整条**路径**映到一个数，比如“沿这条路径走完要花多少时间”。
“使泛函取最小值”就是：在所有可能的路径中，挑出那个让这个数最小的。

费马原理不说光“每一步该往哪拐”，它只说“最终的路径是用时最短的那条”。这是一种**声明**：它规定了答案应当满足的性质，
而不是给出一步步构造答案的配方。斯涅尔定律是这个声明的**推论**：只要路径是最快的，两个角的正弦之比就必须等于速度之比。
:::

下面的小工具让你亲手体验这两种视角。拖动水面上的圆点，你在挑选一条“候选路径”；下方的曲线显示每条候选路径的总用时。
“命令式”按钮每次只看脚下的坡度、往下走一小步（这就是数值优化里的**梯度下降**）；“声明式”按钮则直接在所有候选者中挑出最优者。
两种方法到达的是同一个点——而在那个点上，斯涅尔定律恰好成立。

整个经典力学都可以从**最小作用量原理**推导出来。对任意一条轨迹，都可以通过对**拉格朗日量**积分算出它的**作用量**；
拉格朗日量是动能与势能之**差**（注意：是差，不是和——和是总能量）。当你发射一枚迫击炮弹去打一个给定的目标时，
炮弹会先往上飞，飞到重力势能较高的地方，在那里待上一阵子，给作用量攒下负的贡献。它还会在抛物线的顶端减速，以使动能最小。
然后它会加速，飞快地穿过势能低的区域。

![迫击炮弹](/img/2.1/mortar.jpg "迫击炮弹的抛物线轨迹：在高处慢慢“享受”高势能，在低处飞快掠过。")

费曼最伟大的贡献，是认识到最小作用量原理可以推广到量子力学。在那里，问题同样是用初始状态和最终状态来表述的。
这两个状态之间的**费曼路径积分**，被用来计算跃迁的概率。

![费曼路径积分](/img/2.1/feynman.jpg "费曼路径积分：粒子从初态到末态的所有可能路径都有贡献。")

要点在于：我们描述物理定律的方式中，存在一种奇特的、尚未得到解释的二元性。我们可以使用局部图景，其中事情按顺序、以微小增量发生；
也可以使用全局图景，其中我们**声明**初始条件和最终条件，而中间的一切随之而来。

全局方法也可以用在编程中，比如实现**光线追踪**。我们声明眼睛的位置和光源的位置，然后算出连接它们的光线可能走的路径。
我们并不会显式地为每条光线求最短飞行时间，但我们确实使用了斯涅尔定律和反射的几何关系，效果是一样的。

局部方法和全局方法最大的区别，在于它们对待**空间**、以及更重要的——**时间**的方式。局部方法拥抱此时此地的即时满足；
而全局方法采取一种长远的、静态的视角，仿佛未来早已注定，我们只是在分析某个永恒宇宙的性质。

这一点在用户交互的**函数式响应式编程**（Functional Reactive Programming，FRP）方法中体现得淋漓尽致。
FRP 不是为每种可能的用户操作分别编写处理函数、让它们都能访问某个共享的可变状态，而是把外部事件看作一个**无穷列表**，
并对它施加一系列变换。从概念上讲，我们未来所有操作的列表就摆在那儿，作为程序的输入数据。
从程序的角度看，$\pi$ 的各位数字组成的列表、一个伪随机数列表、或者一个通过计算机硬件传进来的鼠标位置列表，三者没有区别。
无论哪种情况，如果你想取第 $n$ 项，都得先经过前 $n-1$ 项。当这种性质用于时间上的事件时，我们称之为**因果性**（causality）。

::: tip Lean 深入：Lean 里的“无穷列表”
Haskell 的列表是惰性的，可以是无穷的；Lean 的 `List` 是严格的、有限的归纳类型，写不出无穷列表。
一种简单的替代是把“流”表示为从时间（自然数）到值的**函数**：第 $n$ 项就是 `s n`。在这种表示下，
`map` 就是函数复合，“取前 n 项”就是在 `0, 1, …, n-1` 上求值：

```lean
/-- 流：每个时刻 n 都有一个值。 -/
def Stream' (α : Type) : Type := Nat → α

def Stream'.map {α β : Type} (f : α → β) (s : Stream' α) : Stream' β := f ∘ s

def Stream'.take {α : Type} (n : Nat) (s : Stream' α) : List α := (List.range n).map s

/-- 一个“事件流”：第 n 个时刻鼠标的横坐标（这里用一个公式假装一下）。 -/
def mouseX : Stream' Int := fun n => 100 + 3 * n

#guard (mouseX.map (· - 100)).take 4 == [0, 3, 6, 9]
```

不过，函数表示不能体现因果性：`s 1000` 可以直接算，不必先算前 999 项。真实的事件流来自硬件，未来的值还不存在。
Lean 核心库目前没有余归纳（coinductive）的流类型，严肃的 FRP 需要在 `IO` 里用回调或通道来实现。
:::

::: tip Rust 视角：`Iterator` 就是惰性的流
在 Rust 里，惰性、可能无穷的序列是一等公民：`Iterator` 本身就是“要一个、给一个”的流，天然满足因果性——
要拿第 $n$ 个，必须先 `next()` 前 $n-1$ 次。下面把一串（无穷的）“鼠标事件”经过一系列变换，只在最后取需要的部分：

```rust
/// 一个无穷的鼠标横坐标流（这里用公式模拟硬件输入）。
fn mouse_x() -> impl Iterator<Item = i64> {
    (0..).map(|n| 100 + 3 * n)
}

/// 声明式地描述“对事件流做什么”：去掉偏移、只保留偶数、取前 3 个。
fn first_even_offsets() -> Vec<i64> {
    mouse_x().map(|x| x - 100).filter(|d| d % 2 == 0).take(3).collect()
}

#[test]
fn check() {
    assert_eq!(first_even_offsets(), vec![0, 6, 12]);
}
```
:::

那么，这一切和范畴论有什么关系？我要论证的是：范畴论鼓励全局的方法，因此支持声明式编程。
首先，与微积分不同，范畴论没有内建的距离、邻域或时间的概念。我们所有的只是抽象的对象，以及它们之间抽象的连接。
如果你能通过一连串步骤从 $A$ 走到 $B$，你也就能一步跳过去（这正是复合）。
其次，范畴论的主要工具是**泛构造**，而泛构造正是全局方法的典范。我们已经见过它的实际运用，比如范畴论中积的定义。
那是通过指定它的**性质**来完成的——一种非常声明式的做法。积是一个配备了两个投影的对象，并且是所有这样的对象中**最好的**那一个——
它使某种性质达到最优：即“分解其他候选对象的投影”的性质。

![积的候选者排名](/img/2.1/productranking.jpg "积的泛构造：在所有带着两个投影的候选者中，挑出“最好”的那一个——其他候选者都能唯一地经由它分解。")

拿这个和费马最短时间原理、或者最小作用量原理比较一下。

反过来，再对比一下笛卡尔积的传统定义，它要命令式得多。你描述的是如何创建积的一个元素：从一个集合中挑一个元素，再从另一个集合中挑一个元素。
这是一份创建对的配方。另外还有一份拆开对的配方。

在 Lean 里，这两种视角可以并排摆出来。“配方”式的定义就是核心库里的 `Prod`：构造子 `(a, b)` 负责组装，`Prod.fst`、`Prod.snd` 负责拆开。
“声明”式的定义则是一个**命题**：它不说积是怎么造出来的，只说积必须满足什么性质。然后我们证明配方确实满足声明：

```lean
/-- 积的泛性质（声明式）：`P` 连同投影 `p`、`q` 是 `a` 与 `b` 的积，
    当且仅当任何候选者 `(c, p', q')` 都能经由唯一的 `m : c → P` 分解。 -/
def IsProduct (P a b : Type) (p : P → a) (q : P → b) : Prop :=
  ∀ (c : Type) (p' : c → a) (q' : c → b),
    ∃ m : c → P, (p ∘ m = p' ∧ q ∘ m = q') ∧
      ∀ m' : c → P, p ∘ m' = p' → q ∘ m' = q' → m' = m

/-- 配方（命令式的 `Prod`）满足声明。 -/
theorem prod_isProduct (a b : Type) : IsProduct (a × b) a b Prod.fst Prod.snd := by
  intro c p' q'
  -- 存在性：m 把 x 送到 (p' x, q' x)
  refine ⟨fun x => (p' x, q' x), ⟨rfl, rfl⟩, ?_⟩
  -- 唯一性：任何满足条件的 m' 都等于 m
  intro m' h₁ h₂
  funext x
  subst h₁
  subst h₂
  rfl
```

::: tip Lean 深入：`refine` 与 `subst`
- `refine ⟨w, 证明₁, ?_⟩` 一次性给出存在量词的见证 `w` 和一部分证明，把写成 `?_` 的部分留作新的目标。
- `subst h₁`：`h₁ : Prod.fst ∘ m' = p'` 的右边是一个局部变量 `p'`，`subst` 就把 `p'` 处处替换成左边。
  替换之后，目标变成 `m' x = ((Prod.fst ∘ m') x, (Prod.snd ∘ m') x)`，而这按积类型的“结构 η 规则”在定义上成立，`rfl` 收尾。
:::

几乎在所有编程语言中——包括 Haskell 这样的函数式语言，也包括 Lean 和 Rust——积类型、余积类型和函数类型都是**内建**的，
而不是用泛构造定义出来的。（在 Lean 里，`structure` 和 `inductive` 是内建机制，`Prod`、`Sum` 都是用它们定义的；
函数类型 `α → β` 则是类型论最底层的原语。）不过，也有人尝试过创造**范畴论式的编程语言**
（例如可以参阅[萩野达也（Tatsuya Hagino）的博士论文](http://web.sfc.keio.ac.jp/~hagino/thesis.pdf)）。

无论是否被直接使用，范畴论的定义都为已有的编程构造提供了正当性，并催生出新的构造。最重要的是，
范畴论提供了一种在声明式层面上对计算机程序进行推理的**元语言**。它还鼓励我们在把问题规约落实为代码**之前**，先对它进行推理。

::: tip Lean 深入：先写规约，再写代码
Lean 让“先对规约推理”变成了一种日常工作方式。你可以先把“我想要什么”写成一个命题，比如上面的 `IsProduct`，
或者“`sumSqImp` 与 `sumSqDecl` 相等”；然后再去写实现、再去证明实现满足规约。规约是声明式的，实现可以是命令式的，
而证明保证了两者之间不会走样。这本书接下来的每一章，几乎都会以这种方式工作：先用范畴论**声明**一个构造应当满足的泛性质，
再在 Lean 里给出它的具体实现，并证明实现确实满足那个性质。
:::

## 补充：从局部到全局，用 Lean 证明一次

上面的 `simulate` 是“局部”的：一步一步地往前推。中学物理课本里还有一个“全局”的答案——匀加速运动的公式：
$v = v_0 + a t$，$x = x_0 + v_0 t + \frac{1}{2} a t^2$。这两种描述会一致吗？浮点数会带来误差（上面的模拟得到 0.99，而公式给出 1.0），
所以我们换成整数、取时间步长为 1，再让 Lean 证明：**无论走多少步**，逐步模拟的结果都与公式完全吻合。

```lean
structure State where
  pos : Int
  vel : Int
deriving Repr, DecidableEq

/-- 局部：一个时间步。 -/
def tick (acc : Int) (s : State) : State :=
  { pos := s.pos + s.vel, vel := s.vel + acc }

/-- 局部：走 n 步。 -/
def run (acc : Int) : Nat → State → State
  | 0,     s => s
  | n + 1, s => run acc n (tick acc s)

/-- 全局：n 步之后的速度 = 初速度 + n × 加速度。 -/
theorem run_vel (acc : Int) (n : Nat) (s : State) :
    (run acc n s).vel = s.vel + n * acc := by
  induction n generalizing s with
  | zero => simp [run]
  | succ n ih =>
    simp only [run, ih, tick]
    push_cast
    rw [Int.add_mul, Int.one_mul]
    omega

/-- 全局：n 步之后的位置（两边乘 2 以避开除法）：2x = 2x₀ + 2n·v₀ + n²·a − n·a。 -/
theorem run_pos (acc : Int) (n : Nat) (s : State) :
    2 * (run acc n s).pos = 2 * s.pos + 2 * n * s.vel + n * n * acc - n * acc := by
  induction n generalizing s with
  | zero => simp [run]
  | succ n ih =>
    simp only [run, ih, tick]
    push_cast
    simp only [Int.mul_add, Int.add_mul, Int.one_mul, Int.mul_one, Int.mul_assoc]
    omega

#guard run 2 100 ⟨0, 0⟩ == ⟨9900, 200⟩
```

::: tip Lean 深入：`induction … generalizing s` 与 `omega`
- `run` 每走一步，状态 `s` 都会变成 `tick acc s`。所以归纳假设必须对**任意**起始状态成立，而不只是最初那个 `s`；
  `generalizing s` 就是告诉 Lean：“把 `s` 也放进归纳假设的 ∀ 里”。
- `push_cast` 把 `((n + 1 : Nat) : Int)` 这样的类型转换往里推，变成 `(n : Int) + 1`。
- `omega` 是一个**线性**整数算术的判定过程：只要目标是由加减法、乘常数、比较组成的，它就能自动证明。
  它不认识两个变量相乘，但会把 `↑n * acc` 这样的乘积当作一个整体“原子”；前面用 `Int.mul_assoc` 等引理把乘积整理成统一的形状，
  正是为了让同一个乘积在两边长得一模一样。
:::

这条定理本身就是本章主题的缩影：`run` 是命令式的配方，定理的右边是声明式的描述，而**证明**在两者之间架起了一座桥。

## 本章小结

- **命令式**告诉计算机“怎么做”：一串按时间排列的步骤；**声明式**告诉它“做什么”：描述结果应当满足的性质。
- 复合本身就有两种写法：`h := g ∘ f`（声明式）与 `let y := f x; g y`（命令式）。在 Lean 里它们是同一个函数（`rfl`）；
  循环与 `map`/`foldl` 管道也可以被证明相等。
- 物理学中有同样的二元性：**局部**的微分方程（逐步积分，像命令式程序）与**全局**的极值原理（费马原理、最小作用量原理、费曼路径积分，像声明式规约）。
- 斯涅尔定律是费马原理的推论；“梯度下降一小步一小步地走”与“直接挑出最优者”到达同一个答案。
- 在 Lean 中，我们证明了逐步模拟 `run` 与匀加速运动公式对任意步数都一致——证明在局部配方与全局描述之间架起了桥。
- FRP 把未来的事件看作一个无穷的流；Lean 的 `List` 是有限的，可以用 `Nat → α` 粗略建模；Rust 的 `Iterator` 则是天然惰性、满足因果性的流。
- 范畴论没有距离与时间，只有对象与箭头；它的核心工具**泛构造**是全局方法的典范：积是所有候选者中“最好”的那一个。
- 范畴论为编程构造提供了正当性，并且是一种在声明式层面上推理程序的元语言；Lean 让“先写规约、再写实现、再证明二者一致”成为日常。
