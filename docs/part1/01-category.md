# 1.1 范畴：复合的本质

范畴是一个简单得让人不好意思的概念。一个**范畴**（category）由一些**对象**（object）和在对象之间穿梭的**箭头**（arrow）组成。所以范畴特别容易画出来：对象画成一个圆圈或一个点，箭头嘛……就画成一支箭头。（为了换换口味，我偶尔会把对象画成小猪，把箭头画成烟花。）但范畴的本质是**复合**（composition）。或者，你更喜欢反过来说也行：复合的本质就是范畴。箭头可以复合：如果有一支从对象 $A$ 指向对象 $B$ 的箭头，又有一支从对象 $B$ 指向对象 $C$ 的箭头，那么就一定有一支从 $A$ 指向 $C$ 的箭头——它们的复合。

![小猪 A、B、C 与烟花箭头](/img/1.1/img_1330.jpg "在范畴中，若有从 A 到 B 的箭头、又有从 B 到 C 的箭头，就必然还有一支从 A 直达 C 的箭头，即它们的复合。这张图还不是一个完整的范畴，因为它缺少恒等态射（见后文）。")

## 箭头即函数

这就已经算“抽象的胡言乱语”了吗？别灰心，我们来点具体的。把箭头（它们也叫**态射**，morphism）想象成函数。你有一个函数 $f$，它接受一个类型为 $A$ 的参数，返回一个 $B$。你还有另一个函数 $g$，它接受一个 $B$，返回一个 $C$。把 $f$ 的结果交给 $g$，你就把它们复合了起来——你刚刚定义了一个新函数：接受一个 $A$，返回一个 $C$。

```diagram
A: (0, 0)
B: (1.6, 1)
C: (3.2, 0)
f: A -> B "f" side=right
g: B -> C "g" side=right
gf: A -> C "g \circ f"
path "先走 f，再走 g": f g
path "直接走 g ∘ f": gf color=green
caption: 两条路径起点相同、终点相同：先 f 后 g，等于一步走完 g ∘ f。
```

在数学里，这种复合写作两个函数之间加一个小圆圈：$g \circ f$。注意复合的顺序是**从右往左**的。有些人会觉得这很别扭。你可能熟悉 Unix 的管道写法，比如：

```text
lsof | grep Chrome
```

或者 F# 里的 `>>`，再或者 Rust 里一路点下去的方法链 `iter().map(..).filter(..)`——它们都是从左往右读的。但在数学里（以及在 Lean 里），函数是从右往左复合的。把 $g \circ f$ 读成“g **在** f **之后**”会有帮助。

::: info 数学小课堂：函数与复合
**函数** $f : A \to B$ 是一条规则：给 $A$ 中的**每一个**元素，指定 $B$ 中**恰好一个**元素。$A$ 叫定义域（domain），$B$ 叫陪域（codomain）。

例子：$A$ 是所有字符串，$B$ 是所有自然数，$f$ = “取字符串的长度”。$g : \mathbb{N} \to \text{Bool}$ = “是不是偶数”。那么

$$(g \circ f)(\text{"范畴"}) = g(f(\text{"范畴"})) = g(2) = \text{true}.$$

记号 $(g \circ f)(x) = g(f(x))$ 解释了为什么要从右往左：写在右边的 $f$ 离 $x$ 更近，所以先作用。只有当 $f$ 的陪域和 $g$ 的定义域**是同一个**东西时，$g \circ f$ 才有意义——这就是“首尾相接”。
:::

我们用一点 Rust 代码把这件事说得更明白（原书这里用的是 C）。有一个函数 `f`，接受类型为 `A` 的参数，返回类型为 `B` 的值；还有一个函数 `g`，接受 `B`，返回 `C`。它们的复合是：

```rust
struct A;
struct B;
struct C;

fn f(a: A) -> B { B }
fn g(b: B) -> C { C }

fn g_after_f(a: A) -> C {
    g(f(a))
}
```

你又一次看到了从右往左的复合：`g(f(a))`，这次是在 Rust 里。

我很想告诉你，Rust 标准库里有一个现成的函数，接受两个函数、返回它们的复合——可惜并没有。（原书作者当年对 C++ 标准库发出了同样的叹息。）当然，Rust 的闭包和泛型足够强大，我们可以自己写一个：

```rust
fn compose<A, B, C>(g: impl Fn(B) -> C, f: impl Fn(A) -> B) -> impl Fn(A) -> C {
    move |x| g(f(x))
}

fn demo() {
    let len = |s: &str| s.chars().count();
    let is_even = |n: usize| n % 2 == 0;
    let even_len = compose(is_even, len);
    assert!(even_len("范畴"));
}
```

能用，但三个类型参数、`impl Fn`、`move` 一个都少不了。所以现在换个口味，试试 Lean。下面是一个从 `A` 到 `B` 的函数的声明：

```lean no-check
f : A → B
```

类似地：

```lean no-check
g : B → C
```

它们的复合是：

```lean no-check
g ∘ f
```

为了让这几行真的能被 Lean 检查，我们需要先告诉 Lean：`A`、`B`、`C` 是任意的类型，`f`、`g` 是任意的这类函数。这正是 `variable` 的用途：

```lean
section
variable {A B C : Type} (f : A → B) (g : B → C)

#check g ∘ f      -- g ∘ f : A → C
example : A → C := g ∘ f
end
```

一旦你见识过在 Lean 里事情能有多简单，再回头看那些表达不了“把两个函数接起来”这种直白概念的语言，就会觉得有点尴尬。而且 Lean 从一开始就拥抱 Unicode：函数箭头本来就写作 `→`（在编辑器里输入 `\to`，或者直接写 ASCII 的 `->`），复合就写作数学里的那个小圆圈 `∘`（输入 `\comp` 或 `\circ`）。不需要任何额外的扩展或设置。

来个具体的例子：

```lean
def len : String → Nat := String.length
def isEven : Nat → Bool := fun n => n % 2 == 0

#guard (isEven ∘ len) "范畴" == true     -- "范畴" 有 2 个字符
#guard (isEven ∘ len) "函子们" == false
```

于是，第一堂 Lean 课来了：**单冒号 `:` 的意思是“具有类型……”**。（Haskell 用的是双冒号 `::`，Lean 和数学一样用单冒号。）在两个类型之间插入一个箭头，就构成一个函数类型。在两个函数之间插入一个小圆圈 `∘`，就把它们复合起来。

::: tip Lean 深入：`∘`、`#check`、`#guard` 与管道
- `g ∘ f` 只是 `Function.comp g f` 的记号，它的定义就是 `fun x => g (f x)`。`fun x => …` 是 Lean 的匿名函数，相当于 Rust 的闭包 `|x| …`。
- `#check e` 让 Lean 告诉你表达式 `e` 的类型；`#eval e` 计算 `e` 的值；`#guard e` 计算一个布尔表达式，**如果不是 `true` 就报错**——所以本书里 `#guard` 后面写的结果都是被机器检查过的。
- `section … end` 划出一个小作用域，里面的 `variable` 声明到 `end` 就失效，不会污染后面的代码。
- 如果你实在想从左往右写，Lean 也有管道：`"范畴" |> len |> isEven` 等价于 `isEven (len "范畴")`。`|>` 就是 Lean 版的 Unix `|`。
:::

## 复合的性质

任何范畴中的复合都必须满足两条极其重要的性质。

**1. 复合满足结合律。** 如果你有三个态射 $f$、$g$、$h$，它们可以复合（也就是说，它们的对象首尾相接），那么复合它们时不需要括号。用数学记号写就是：

$$h \circ (g \circ f) = (h \circ g) \circ f = h \circ g \circ f$$

原书在这里用的是“伪 Haskell”，并特意说明“之所以说‘伪’，是因为函数之间并没有定义相等”。在 Lean 里我们不需要“伪”——这就是一条真正的定理，而且证明只有三个字母：

```lean
theorem comp_assoc' {A B C D : Type} (f : A → B) (g : B → C) (h : C → D) :
    h ∘ (g ∘ f) = (h ∘ g) ∘ f := rfl
```

```diagram
A: (0, 0)
B: (2, 0)
C: (2, 1.6)
D: (0, 1.6)
f: A -> B "f"
g: B -> C "g"
h: C -> D "h"
gf: A -> C "g \circ f" pos=0.35
hg: B -> D "h \circ g" pos=0.35
path "h ∘ (g ∘ f)：先走 g∘f，再走 h": gf h
path "(h ∘ g) ∘ f：先走 f，再走 h∘g": f hg color=green
caption: 结合律：无论先把 f、g 粘在一起，还是先把 g、h 粘在一起，从 A 走到 D 得到的都是同一支箭头。
```

::: tip Lean 深入：函数的相等、`rfl` 与 `=` / `==`
- 在 Lean 里，`a = b` 是一个**命题**（proposition），它本身也是一个类型；证明它，就是构造这个类型的一个值。
- `rfl`（reflexivity，自反性）是最基本的证明：“两边算出来是同一个东西”。Lean 会把两边都展开、化简：`h ∘ (g ∘ f)` 和 `(h ∘ g) ∘ f` 展开后都是 `fun x => h (g (f x))`，所以 `rfl` 就够了。
- 注意 `=` 和 `==` 的区别：`==` 是**运行时**的布尔比较（来自 `BEq` 类型类，对应 Rust 的 `PartialEq`）；函数没有 `BEq` 实例，你不能在程序里“比较两个函数是否相等”，这一点和 Haskell、Rust 一样。但 `=` 是**逻辑上**的相等，函数之间完全可以谈论、可以证明。Lean 有一条定理 `funext`（函数外延性）：如果两个函数对每个输入都给出相同输出，它们就相等。
:::

对函数来说，结合律相当显然；但在别的范畴里，它可能就没那么显然了。

**2. 每个对象都有一支作为复合单位的箭头。** 对每个对象 $A$，都有一支从 $A$ 绕回 $A$ 自身的箭头，它是复合的**单位**：把它和任何一支从 $A$ 出发、或者到达 $A$ 的箭头复合，得到的还是原来那支箭头。对象 $A$ 上的单位箭头叫做 $\mathrm{id}_A$（$A$ 上的**恒等态射**，identity）。用数学记号写：如果 $f$ 从 $A$ 到 $B$，那么

$$f \circ \mathrm{id}_A = f$$

并且

$$\mathrm{id}_B \circ f = f$$

```diagram
A: (0, 0)
B: (2.2, 0)
f: A -> B "f"
idA: A -> A "\mathrm{id}_A" loop=left
idB: B -> B "\mathrm{id}_B" loop=right
path "f ∘ id_A": idA f
path "id_B ∘ f": f idB color=orange
path "只走 f": f color=green
caption: 恒等律：在 f 之前或之后绕一圈恒等箭头，等于什么都没做。
```

::: info 数学小课堂：结合律与单位元，你早就认识
- **结合律**你在小学就见过：$(2+3)+4 = 2+(3+4)$，所以可以干脆写 $2+3+4$。乘法也一样。但减法就**不**满足结合律：$(8-4)-2 = 2$，而 $8-(4-2) = 6$。所以“满足结合律”是一条真正的限制，不是废话。
- **单位元**就是“加上它等于没加”的东西：加法的单位元是 $0$（$x + 0 = x$），乘法的单位元是 $1$（$x \times 1 = x$），字符串拼接的单位元是空串 `""`。恒等态射 $\mathrm{id}_A$ 就是“复合”这种运算的单位元。
- 不同之处在于：$0$ 只有一个，而恒等态射是**每个对象各有一个**，$\mathrm{id}_A$ 和 $\mathrm{id}_B$ 是不同的箭头。
:::

在函数的世界里，恒等箭头就实现为恒等函数：原样返回自己的参数。它对每个类型的实现都一样，这意味着这个函数是**全称多态**（universally polymorphic）的。在 Rust 里可以用泛型来定义它：

```rust
fn id<T>(x: T) -> T {
    x
}
```

在 C++ 里事情从来没这么简单，因为你不仅要考虑传什么，还得考虑**怎么**传（按值、按引用、按 const 引用、按移动……）。Rust 在这里干净得多：`T` 可以是任何类型——包括引用类型 `&U` 或 `&mut U`——所以这一个定义就涵盖了所有“传法”；按值传入时，所有权移进来，再原样移出去。

在 Lean 里，恒等函数是核心库的一部分（巧的是，它就定义在一个叫 `Init.Prelude` 的文件里——和 Haskell 标准库的名字 Prelude 一样）。我们自己写一遍它的声明和定义：

```lean
def myId {α : Type} (x : α) : α := x

#guard myId 42 == 42
#guard myId "猪" == "猪"
```

如你所见，Lean 里的多态函数易如反掌。在声明中，你只要把具体类型换成一个**类型变量**即可。这里的 `{α : Type}` 说：“`α` 是某个类型”。花括号表示它是**隐式参数**——调用时不用写，Lean 会根据你传进来的 `x` 自己推断出 `α` 是什么，就像 Rust 推断 `id::<T>` 里的 `T` 一样。所以 `α` 代表任意类型。（Haskell 靠大小写区分具体类型和类型变量；Lean 没有这种规则，惯例是用希腊字母 `α β γ` 当类型变量，用 `\a`、`\b`、`\g` 输入。）

Lean 的函数定义由 `def`、函数名、形式参数（这里只有一个 `(x : α)`）、冒号后的返回类型组成，函数体写在 `:=` 之后。新手常被这种简洁吓一跳，但你很快就会发现它非常合理。函数定义和函数调用是函数式编程的家常便饭，所以它们的语法被精简到了极致。调用时，参数列表既不用括号包起来，参数之间也不用逗号分隔：`myId 42` 就是“把 `myId` 作用于 `42`”。（以后定义多参数函数时你会看到，`f x y` 就是传两个参数。）

函数体永远是一个**表达式**——函数里没有“语句”。函数的结果就是这个表达式的值——这里就是 `x`。（Rust 程序员对此应该很亲切：Rust 的块 `{ … }` 也是表达式，最后一个不带分号的表达式就是块的值。Lean 只是把这个习惯贯彻到底。）

第二堂 Lean 课到此结束。

::: tip Lean 深入：核心库里的 `id`
在 Lean 里输入 `#check @id`，会看到 `@id : {α : Sort u} → α → α`。它比我们的 `myId` 更通用一点：`Sort u` 不但包括所有“数据类型”，还包括“命题”。现在你可以把 `Sort u` 当成 `Type` 的加强版，后面讲宇宙时再细说。`@id` 前面的 `@` 表示“把隐式参数也显示出来”。
:::

恒等条件可以写成下面的样子。原书在这里又只能写“伪 Haskell”，而我们照例直接证明：

```lean
section
variable {A B : Type} (f : A → B)

example : f ∘ myId = f := rfl
example : myId ∘ f = f := rfl
end
```

为什么 `rfl` 能证明它们？`f ∘ myId` 展开是 `fun x => f (myId x)`，`myId x` 化简成 `x`，于是得到 `fun x => f x`；而 `fun x => f x` 和 `f` 本身在 Lean 看来就是同一个东西（这叫 η-等价）。所以两边“算出来一样”。

你也许会问自己：为什么会有人费心去研究恒等函数——一个什么都不做的函数？那么话说回来，我们为什么要费心研究数字零呢？零是“什么都没有”的符号。古罗马人的计数系统里没有零，可他们照样修出了出色的道路和引水渠，其中一些留存至今。

像零或 $\mathrm{id}$ 这样的中性值，在处理符号变量时极其有用。这就是为什么罗马人不太擅长代数，而熟悉零这个概念的阿拉伯人和波斯人却很擅长。同样，恒等函数作为高阶函数的参数或返回值时非常顺手。高阶函数使得对函数进行符号操作成为可能——它们是函数的代数。

::: tip Rust 视角：`id` 什么时候有用？
你多半写过 `.filter_map(|x| x)` 或 `.flat_map(|x| x)`——那个 `|x| x` 就是恒等函数（标准库里叫 `std::convert::identity`）。再比如一个“可选的变换”参数 `transform: impl Fn(T) -> T`，调用者不想变换时就传 `identity`。零在加法里的角色，`identity` 在函数复合里扮演。
:::

总结一下：一个范畴由对象和箭头（态射）组成。箭头可以复合，复合满足结合律。每个对象都有一支恒等箭头，充当复合的单位。

下面的小组件让你亲手玩一个具体的范畴。它有四个对象 $A, B, C, D$，三支“生成”箭头 $f, g, h$，三支复合出来的箭头 $u, v, w$，以及四支恒等箭头。试着点出 $h \circ g \circ f$，再看看两种加括号方式是怎样殊途同归的；也试试点一支首尾不相接的箭头会发生什么。

## 补充：用 Lean 写下范畴的定义

到目前为止，“范畴”还只是一段文字描述。Lean 的强项在于：我们可以把这段描述**一字不差地写成代码**，连同那两条定律一起，让编译器替我们把关。本书所有章节都使用同一份定义（放在 `lean/Prelude.lean` 里），这里第一次完整地展示它，并逐行讲解。

### 类 `Category`

```lean
universe u v

namespace CTFP

/-- 范畴：对象 + 态射 + 复合 + 恒等，满足单位律与结合律。 -/
class Category (Obj : Type u) where
  /-- 从 `a` 到 `b` 的态射所组成的类型（hom-set）。 -/
  Hom : Obj → Obj → Type v
  /-- 每个对象上的恒等态射。 -/
  id : (a : Obj) → Hom a a
  /-- 复合：`comp g f` 表示先 `f` 后 `g`。 -/
  comp : {a b c : Obj} → Hom b c → Hom a b → Hom a c
  id_comp : ∀ {a b : Obj} (f : Hom a b), comp (id b) f = f := by intros; rfl
  comp_id : ∀ {a b : Obj} (f : Hom a b), comp f (id a) = f := by intros; rfl
  assoc : ∀ {a b c d : Obj} (f : Hom a b) (g : Hom b c) (h : Hom c d),
    comp h (comp g f) = comp (comp h g) f := by intros; rfl
```

我们一行一行来看。

**`universe u v`**：声明两个**宇宙变量**。先不用细究，下面的“数学小课堂”会解释；你暂时可以把 `Type u` 读作“某一层的类型”。

**`namespace CTFP`**：把接下来的定义都放进命名空间 `CTFP`（Category Theory for Programmers）里，这样我们的 `Category.id` 就不会和核心库的 `id` 打架。它相当于 Rust 的 `mod ctfp { … }`。

**`class Category (Obj : Type u) where`**：定义一个**类型类**（type class）。类型类就是 Rust 里 trait 的近亲：它描述“一个类型要成为范畴，必须提供哪些东西”。参数 `Obj` 是“对象所组成的类型”——比如对象是所有自然数时，`Obj` 就是 `Nat`。

**`Hom : Obj → Obj → Type v`**：对任意两个对象 `a b`，`Hom a b` 是“从 `a` 到 `b` 的所有箭头”组成的类型，也就是 **hom-集**（hom-set，即态射集合）。注意这个字段的值本身是一个**返回类型的函数**：给它两个对象，它还你一个类型。Rust 的 trait 可以有关联类型（`type Hom;`），但关联类型不能依赖于两个**值** `a`、`b`——这种“类型依赖于值”的能力就是 Lean 的**依值类型**（dependent type），也是 Lean 能把数学写得如此直接的原因。

**`id : (a : Obj) → Hom a a`**：每个对象 `a` 都有一支恒等箭头，类型是 `Hom a a`（从 `a` 回到 `a`）。写法 `(a : Obj) → …` 给参数起了名字 `a`，这样箭头右边的返回类型才能提到它——返回类型**依赖于**传进来的那个对象。

**`comp : {a b c : Obj} → Hom b c → Hom a b → Hom a c`**：复合。给我一支 `b → c` 的箭头和一支 `a → b` 的箭头，我还你一支 `a → c` 的箭头。几个要点：

- 参数顺序是“先 `g` 后 `f`”，和数学的 $g \circ f$ 一致：`comp g f` 表示先 `f` 后 `g`。
- `{a b c : Obj}` 是**隐式参数**。调用 `comp g f` 时你不用写出 `a b c`，Lean 会从 `g`、`f` 的类型中自动读出来。这和 Rust 泛型参数被自动推断是一回事，只不过这里被推断的是**对象**（值），而不仅仅是类型。
- 最妙的一点：**“首尾相接”是由类型检查器强制的**。`f` 的终点和 `g` 的起点必须是同一个 `b`，否则 `comp g f` 根本无法通过编译。原书反复强调“只有首尾相接的箭头才能复合”，在 Lean 里这是一条类型规则。

**`id_comp`、`comp_id`、`assoc`**：三条定律——左单位律、右单位律、结合律。它们也是类的字段，只不过类型是**命题**，比如

```lean no-check
∀ {a b : Obj} (f : Hom a b), comp (id b) f = f
```

读作：“对所有对象 `a b`、所有箭头 `f : a ⟶ b`，`id b` 复合 `f` 等于 `f`。”一个类型要成为 `Category` 的实例，不但要提供 `Hom`、`id`、`comp`，还必须**交出这三条定律的证明**。证明就是数据，这正是 Lean 的精神。

**`:= by intros; rfl`**：这是字段的**默认值**。如果某个实例没有亲自提供证明，Lean 就会自动尝试 `by intros; rfl`：引入所有变量，然后看两边能不能“算到一起”。对很多简单的范畴，这就够了，于是定律可以省略不写——下面马上会看到。（`by` 后面跟的是**策略**（tactic）脚本：一串告诉 Lean“如何构造证明”的指令。`intros` 把 `∀` 引入的变量变成假设，`rfl` 用自反性收尾。）

::: info 数学小课堂：宇宙——为什么是 `Type u` 而不是 `Type`？
在 Lean 里，`Nat`、`Bool`、`String` 这样的类型，它们自己也有类型：`Nat : Type`。那 `Type` 的类型是什么？如果说 `Type : Type`，就会出事——这相当于集合论里的“所有集合组成的集合”，会导致类似罗素悖论的矛盾（下一章讲“类型即集合”时，Milewski 也会提到“不存在所有集合的集合”这个坑）。

Lean 的解决办法是分层：

$$\texttt{Nat} : \texttt{Type} = \texttt{Type 0},\quad \texttt{Type 0} : \texttt{Type 1},\quad \texttt{Type 1} : \texttt{Type 2},\ \dots$$

每一层叫一个**宇宙**（universe）。`Type u` 中的 `u` 是一个“层号变量”，表示“任意某一层”。

为什么范畴的定义需要它？因为我们马上要定义“所有类型组成的范畴”，它的对象类型 `Obj` 是 `Type` 本身——而 `Type` 住在 `Type 1` 里，不在 `Type 0` 里。如果我们把定义写死成 `Obj : Type`，就装不下它了。写成 `Obj : Type u`、`Hom … : Type v`，就让对象和箭头可以住在任意层。日常编程你几乎不用操心这些：Lean 会自动推断层号。
:::

::: tip Rust 视角：能写进类型的定律
如果用 Rust 写一个 `trait Category`，你能表达 `Hom`、`id`、`comp`，但表达不了定律——最多在文档注释里写一句“实现者必须保证结合律”。Rust 标准库里有很多这样的“君子协定”：`Ord` 必须是全序，`Hash` 必须和 `Eq` 一致，`Iterator::size_hint` 不能撒谎……违反了，编译器不会说一个字，你只会在运行时得到莫名其妙的 bug。

Lean 把这些协定变成了字段：不交证明，实例就写不出来。
:::

### 记号

接下来给常用的东西起几个好看的名字：

```lean
infixr:10 " ⟶ " => Category.Hom
infixr:80 " ⊚ " => Category.comp
notation "𝟙" => Category.id

open Category
```

- `a ⟶ b` 表示 `Category.Hom a b`，即“从 `a` 到 `b` 的箭头的类型”。注意这支长箭头 `⟶`（输入 `\hom`）和函数箭头 `→` 不是同一个符号：`→` 是 Lean 内建的函数类型，`⟶` 是**任意范畴**里的箭头。
- `g ⊚ f` 表示 `Category.comp g f`，读作“g 在 f 之后”（输入 `\circledcirc`）。我们特意没有直接用 `∘`，因为 `∘` 在 Lean 里已经被普通函数复合占用了。
- `𝟙 a` 表示对象 `a` 上的恒等箭头 `Category.id a`（输入 `\b1`）。
- `infixr:80` 中的 `infixr` 表示“右结合的中缀运算符”，`80` 是优先级（数字越大结合得越紧）。所以 `h ⊚ g ⊚ f` 会被解析成 `h ⊚ (g ⊚ f)`；而 `⟶` 的优先级只有 `10`，结合得很松，`a ⟶ b` 两边可以放比较复杂的表达式。
- `open Category` 让我们在这个命名空间里可以直接写 `comp`、`id_comp`，而不必写全名 `Category.comp`。

### 实例：类型与函数构成的范畴

现在来造第一个范畴：对象是（某一层宇宙里的）**所有类型**，从 `a` 到 `b` 的箭头是**所有函数** `a → b`。

```lean
/-- 类型与函数构成的范畴 **Type**（原书中的 **Set**/**Hask**）。三条定律都是 `rfl`。 -/
instance typeCategory : Category (Type u) where
  Hom a b := a → b
  id _ := fun x => x
  comp g f := fun x => g (f x)

end CTFP
```

- `instance typeCategory : Category (Type u)`：声明一个类型类实例，相当于 Rust 的 `impl Category for …`。这里的 `Obj` 是 `Type u`——对象就是类型本身。
- `Hom a b := a → b`：从 `a` 到 `b` 的箭头，就是从 `a` 到 `b` 的函数。
- `id _ := fun x => x`：恒等箭头就是恒等函数。下划线 `_` 表示“这个参数（对象）我不需要给它起名”。
- `comp g f := fun x => g (f x)`：复合就是函数复合，和我们前面写的 `g ∘ f` 一模一样。
- **三条定律一条都没写！** 它们由默认值 `by intros; rfl` 自动补上了。为什么 `rfl` 对函数总能成功？因为 Lean 判断两个表达式“算出来一样”时，会自动做两件事：**β-归约**（把 `(fun x => body) arg` 代入展开成 `body[x := arg]`）和 **η-等价**（`fun x => f x` 就是 `f`）。比如结合律的两边：

$$h \circ (g \circ f) \;\rightsquigarrow\; \lambda x.\ h\,((\lambda y.\ g\,(f\,y))\,x) \;\rightsquigarrow\; \lambda x.\ h\,(g\,(f\,x))$$

$$(h \circ g) \circ f \;\rightsquigarrow\; \lambda x.\ (\lambda y.\ h\,(g\,y))\,(f\,x) \;\rightsquigarrow\; \lambda x.\ h\,(g\,(f\,x))$$

  两边化简到了同一个表达式，所以是 `rfl`。单位律同理：`𝟙 b ⊚ f` 化简成 `fun x => f x`，η-等价于 `f`。

如果你想亲眼看看这个“展开—化简”的过程，可以用 `show` 把目标改写成展开后的形状（`show` 只接受与原目标“算出来一样”的形状，所以它本身就是一次检查）：

::: details 展开看看：恒等律为什么是 `rfl`
```lean
open CTFP

example {a b : Type} (f : a ⟶ b) : 𝟙 b ⊚ f = f := by
  -- 按定义展开 ⊚ 和 𝟙：
  show (fun x => (fun y => y) (f x)) = f
  -- β-归约：(fun y => y) (f x) 就是 f x
  show (fun x => f x) = f
  -- η-等价：fun x => f x 就是 f
  rfl
```
:::

### 用起来

有了这些，就可以在范畴的语言里写普通函数了：

```lean
def inc : Nat ⟶ Nat := fun n => n + 1
def dbl : Nat ⟶ Nat := fun n => n * 2

example : inc ⊚ dbl = fun n => n * 2 + 1 := rfl   -- 先翻倍，再加一
#guard (inc ⊚ dbl) 5 == 11
#guard (dbl ⊚ inc) 5 == 12                         -- 顺序很重要
```

::: warning 易错点：先起名，再复合
如果直接写 `(fun n => n + 1) ⊚ (fun n => n * 2)`，Lean 会抱怨推断不出该用哪个范畴实例——裸 lambda 的类型是 `Nat → Nat`，Lean 不会自动想到“哦，这是 `typeCategory` 里的箭头”。所以要像上面那样，先用 `def inc : Nat ⟶ Nat := …` 给箭头起名并写明类型，再用 `⊚` 复合。
:::

最后，范畴的定义真正的威力在于：**只要从定律出发，证明一次，就对所有范畴都成立**。下面这条定理对任何范畴 `C`（不只是类型与函数）都对：

```lean
theorem id_sandwich {C : Type u} [Category.{u, v} C] {a b : C} (f : a ⟶ b) :
    𝟙 b ⊚ f ⊚ 𝟙 a = f := by
  rw [Category.comp_id]   -- 用右单位律把 f ⊚ 𝟙 a 改写成 f
  rw [Category.id_comp]   -- 再用左单位律把 𝟙 b ⊚ f 改写成 f
```

这里的方括号 `[Category.{u, v} C]` 是**实例参数**：“`C` 是任意一个带有范畴结构的类型”，相当于 Rust 的 `C: Category` 约束。`Category.{u, v}` 显式指定了宇宙层号，你可以忽略它。证明中的 `rw [定理]`（rewrite，改写）会在目标里找到符合定理左边的部分，把它替换成右边。这一次 `rfl` 帮不了我们，因为 `C` 是个未知的范畴，没有什么可以“展开计算”的——我们只能靠定律推理。这正是范畴论的工作方式：不去看对象和箭头的“内部”，只用复合的规则说话。

在 [1.3 大大小小的范畴](/part1/03-categories-great-and-small) 里，我们会遇到许多别的范畴，有些的定律就不再是一个 `rfl` 能打发的了。

## 复合是编程的本质

函数式程序员思考问题的方式很特别。他们一上来就问一些很有禅意的问题。比如，设计一个交互式程序时，他们会问：交互是什么？实现康威的“生命游戏”时，他们大概会沉思生命的意义。本着这种精神，我要问：编程是什么？

在最底层，编程就是告诉计算机该做什么：“取出内存地址 x 中的内容，把它加到寄存器 EAX 的内容上。”但即使用汇编编程，我们下达给计算机的指令也是某种更有意义的东西的表达。我们在解决一个不平凡的问题（如果它平凡，我们就不需要计算机帮忙了）。那我们是怎么解决问题的呢？我们把大问题分解成小问题。如果小问题还太大，就继续分解，如此往复。最后，我们写代码解决所有的小问题。然后，编程的本质登场了：我们把这些代码片段**复合**起来，构成更大问题的解。如果不能把碎片重新拼回去，分解就毫无意义。

这种层层分解、再层层复合的过程，并不是计算机强加给我们的。它反映的是人类心智的局限。我们的大脑一次只能处理少量的概念。心理学界被引用最多的论文之一《[神奇的数字七，加减二](https://en.wikipedia.org/wiki/The_Magical_Number_Seven,_Plus_or_Minus_Two)》提出，我们脑中只能同时保持 $7 \pm 2$ 个信息“块”（chunk）。我们对人类短期记忆的具体认识也许还在变化，但可以肯定，它是有限的。归根结底，我们处理不了一锅对象汤，也处理不了一盘意大利面条式的代码。我们需要结构，不是因为结构良好的程序看着赏心悦目，而是因为不这样，我们的大脑就没法高效地处理它们。我们常说某段代码优雅或漂亮，其实真正的意思是：它容易被我们有限的人类心智处理。优雅的代码切出的块，大小恰好、数量恰好，正适合我们的“心智消化系统”吸收。

那么，对程序的复合来说，什么样的块才是合适的？它们的**表面积**增长得要比**体积**慢。（我喜欢这个类比，因为直觉上，几何体的表面积随尺寸的平方增长——比随尺寸立方增长的体积慢。）表面积是我们**复合**这些块时需要知道的信息；体积是我们**实现**它们时需要知道的信息。其思想是：一个块一旦实现完毕，我们就可以忘掉它的实现细节，专心考虑它如何与其他块交互。在面向对象编程中，表面就是对象的类声明，或者它的抽象接口。在函数式编程中，表面就是函数的声明。（我把事情简化了一点，但大意如此。）

::: tip Rust 视角：表面积与体积
Rust 程序员每天都在和“表面积”打交道：一个 crate 的公开 API（`pub fn` 的签名、`pub trait` 的方法）就是表面，函数体和私有模块就是体积。`fn parse(input: &str) -> Result<Ast, ParseError>` 这一行签名，就足以让你把它和别的函数拼起来，而不必读它内部几千行的实现。写出“签名就说明了一切”的函数，是让代码可复合的关键。Lean 把这一点推得更远：签名里甚至可以写上定律和规格说明。
:::

范畴论在这一点上非常极端：它积极地**劝阻**我们去窥视对象的内部。范畴论中的对象是一个抽象的、朦胧的实体。关于它，你能知道的全部，就是它与其他对象的关系——它如何通过箭头与它们相连。这就像互联网搜索引擎通过分析网站的入链和出链来给网站排名一样（除非它们作弊）。在面向对象编程中，一个理想化的对象只能通过它的抽象接口被看到（纯粹的表面，没有体积），方法扮演着箭头的角色。一旦你不得不挖进对象的实现，才能弄明白如何把它和其他对象复合起来，你就失去了你所用的编程范式的优势。

## 挑战

1. 用你最喜欢的语言（如果你最喜欢的语言恰好是 Haskell，那就用第二喜欢的），尽可能好地实现恒等函数。
2. 用你最喜欢的语言实现复合函数。它接受两个函数作为参数，返回它们的复合。
3. 写一个程序，尝试测试你的复合函数是否尊重恒等函数。
4. 万维网在某种意义上是一个范畴吗？链接是态射吗？
5. Facebook 是一个范畴吗？以人为对象、以好友关系为态射。
6. 什么时候一个有向图是一个范畴？

追加的 Lean 题：

7. 在 Lean 中证明：你在第 2 题写的复合函数满足结合律，并且和恒等函数一起满足两条单位律。

::: details 参考答案：第 1～3 题与第 7 题（Lean）
Lean 版本。我们把它们放进命名空间 `Challenge`，以免和前面的定义重名。

```lean
namespace Challenge

/-- 第 1 题：恒等函数。 -/
def identity {α : Type} (x : α) : α := x

/-- 第 2 题：复合函数，`compose g f` 表示先 `f` 后 `g`。 -/
def compose {α β γ : Type} (g : β → γ) (f : α → β) : α → γ :=
  fun x => g (f x)

/-- 第 3 题：测试——在几个具体的输入上检查。 -/
def addOne (n : Nat) : Nat := n + 1
#guard compose identity addOne 41 == addOne 41
#guard compose addOne identity 41 == addOne 41
#guard (List.range 100).all fun n => compose identity addOne n == addOne n

/-- 第 3 题，升级版：不是“测试”，而是**证明**——对一切函数、一切输入都成立。 -/
theorem compose_identity_left {α β : Type} (f : α → β) :
    compose identity f = f := rfl

theorem compose_identity_right {α β : Type} (f : α → β) :
    compose f identity = f := rfl

/-- 第 7 题：结合律。 -/
theorem compose_assoc {α β γ δ : Type} (f : α → β) (g : β → γ) (h : γ → δ) :
    compose h (compose g f) = compose (compose h g) f := rfl

end Challenge
```

注意第 3 题“测试”和“证明”的差别：`#guard` 只检查了我们挑出来的那 100 个输入，而定理覆盖了**所有**类型、**所有**函数、**所有**输入。下一章 Milewski 会说“测试是证明的拙劣替代品”——在 Lean 里，你可以两样都要。
:::

::: details 参考答案：第 1～3 题（Rust）
```rust
/// 第 1 题：恒等函数。泛型 T 可以是任何类型，包括引用 &U、&mut U。
pub fn identity<T>(x: T) -> T {
    x
}

/// 第 2 题：复合函数，compose(g, f) 表示先 f 后 g。
pub fn compose<A, B, C>(g: impl Fn(B) -> C, f: impl Fn(A) -> B) -> impl Fn(A) -> C {
    move |x| g(f(x))
}

/// 第 3 题：测试复合尊重恒等。
pub fn respects_identity<F>(f: F, inputs: &[i64]) -> bool
where
    F: Fn(i64) -> i64 + Copy,
{
    inputs.iter().all(|&x| {
        compose(identity, f)(x) == f(x) && compose(f, identity)(x) == f(x)
    })
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn composition_respects_identity() {
        let inputs: Vec<i64> = (-1000..=1000).collect();
        assert!(respects_identity(|n| n * 2 + 1, &inputs));
        assert!(respects_identity(|n| n.abs(), &inputs));
    }
}
```

用 `cargo test` 运行。Rust 的测试只能覆盖有限个输入、有限个函数——这已经是“尽可能好”了。要想对**一切**函数都确信，你需要 Lean 那样的证明。
:::

::: details 参考答案：第 4～6 题
**第 4 题（万维网）。** 如果以网页为对象、以超链接为态射，它**不是**范畴：页面 A 链接到 B、B 链接到 C，并不意味着 A 有一个直接链接到 C；而且大多数页面也不链接到自己，没有现成的恒等态射。但如果把态射换成“**链接的路径**”（从一个页面出发、沿着链接点击若干次），那它就是范畴了：两条首尾相接的路径接起来还是路径（复合），接路径显然满足结合律，而“一次也不点”的空路径就是恒等态射。这种由图的路径构成的范畴叫做**自由范畴**（free category），我们在 1.3 中会正式见到它。

**第 5 题（Facebook）。** 以人为对象、好友关系为态射，也**不是**范畴：你的朋友的朋友未必是你的朋友，好友关系不能复合；“自己是自己的好友”也不是 Facebook 上的东西。同样，如果把态射换成“好友链”（你 → 朋友 → 朋友的朋友 → …），就得到一个自由范畴。

**第 6 题（有向图）。** 一个有向图要成为范畴，需要：

- 每个节点上都有一条指定的自环，充当恒等态射；
- 对每一对首尾相接的边 $f : a \to b$、$g : b \to c$，都有一条指定的边 $g \circ f : a \to c$ 作为它们的复合；
- 这种复合满足结合律，并且恒等自环是复合的单位。

一个特别简单的情形是：两个节点之间最多一条边，并且图是**自反的**（每个节点都有自环）和**传递的**（有 $a \to b$ 和 $b \to c$ 的边，就有 $a \to c$ 的边）。这时复合是唯一确定的，定律自动成立。这样的图就是一个**预序**（preorder），1.3 中会详细讨论。例如，以自然数为节点、当 $m \le n$ 时画一条边 $m \to n$：

```lean
open CTFP

/-- 自然数与 ≤：一个“两点间至多一支箭头”的范畴。 -/
instance natLeCategory : Category Nat where
  Hom m n := PLift (m ≤ n)        -- 从 m 到 n 的箭头 = “m ≤ n 的一个证明”
  id n := ⟨Nat.le_refl n⟩          -- 自反性：n ≤ n
  comp g f := ⟨Nat.le_trans f.down g.down⟩   -- 传递性：m ≤ n, n ≤ k ⇒ m ≤ k

def twoToFive : (2 : Nat) ⟶ 5 := ⟨by decide⟩
def fiveToNine : (5 : Nat) ⟶ 9 := ⟨by decide⟩
def twoToNine : (2 : Nat) ⟶ 9 := fiveToNine ⊚ twoToFive
```

这里有几处新东西：`m ≤ n` 是一个**命题**，它的证明不是“数据”，所以要用 `PLift` 把它包装成一个普通的类型才能当 `Hom`；`⟨…⟩` 是匿名构造子，`f.down` 取出包在里面的证明；`by decide` 让 Lean 通过直接计算来证明 `2 ≤ 5` 这样的具体命题。

更有意思的是：**三条定律我们又一条都没写**，`by intros; rfl` 照样成功了。原因是 Lean 认为同一个命题的任意两个证明都相等（证明无关性，proof irrelevance），所以两点之间的箭头至多“只有一支”，复合怎么算都相等。

对**任意**有向图，还有另一种办法得到范畴：取它的所有路径——这就是第 4、5 题里说的自由范畴。
:::

## 本章小结

- **范畴** = 对象 + 箭头（态射）+ 复合 + 恒等箭头，满足**结合律**与**单位律**。仅此而已。
- 复合 $g \circ f$ 读作“g 在 f 之后”，从右往左；只有首尾相接（$f$ 的终点等于 $g$ 的起点）的箭头才能复合。
- 最重要的例子：对象是类型、箭头是函数、复合是函数复合、恒等箭头是恒等函数 `id`。
- 在 Lean 里，`=` 是可以证明的命题。函数复合的结合律、单位律都能用 `rfl` 证明，因为两边化简后完全相同（β-归约与 η-等价）。
- `CTFP.Category` 把范畴的定义写成了一个类型类：`Hom` 是依赖于两个对象的类型（hom-集），`comp` 的类型强制“首尾相接”，三条定律是必须提交证明的字段。
- 记号：`a ⟶ b` 是箭头的类型，`g ⊚ f` 是复合，`𝟙 a` 是恒等箭头；`typeCategory` 让所有类型和函数构成一个范畴。
- 从定律出发证明的定理（如 `id_sandwich`）对一切范畴成立——这就是范畴论“不看内部，只看箭头”的威力。
- 编程的本质是分解与复合；好的模块“表面积小、体积大”，范畴论把这种思想推向极致：对象的一切都由它与其他对象之间的箭头刻画。
